1. How to read this blueprint

Feynman explanation: Think of AutoTest as a restaurant. Excel is the order sheet. The UI is the waiter. Express routes are the kitchen tickets. JSON files are the pantry shelves. The compiler is the chef. Playwright is the delivery driver. A button is only truly connected when the waiter sends the correct ticket, the pantry changes, the chef can use the changed ingredient, and the customer sees the result after the restaurant restarts.

This document uses five labels:

CONNECTED / VERIFIED

Evidence exists that the user-facing operation reaches the expected route, persists to the intended store, survives reload/restart, and is consumed downstream.

IMPLEMENTED / BACKEND-ONLY

A route or unit behavior exists, but the real UI gesture, packaged path, or restart durability has not passed. This is not release acceptance.

BROKEN / RELEASE BLOCKER

User-observed or reproduced behavior prevents a normal tester from completing the intended workflow.

PLANNED

Architectural direction or future work, not a promise that the current build implements it.

OUT OF SCOPE

Explicitly excluded from the current acceptance boundary, such as real-device Appium verification.

Important: Existing API tests prove that an endpoint can work in a test process. They do not prove that a visible button opens, sends the correct payload, writes the packaged writable database, survives restart, or renders its result. The five reported failures remain blockers until interaction-level evidence closes those gaps.

Primary sources: AGENTS.md, FUTURE_ARCHITECTURE.md, TEST_SCENARIOS.md, TEST_RESULTS.md, current code audit.

2. Executive BRD

2.1 Product purpose

AutoTest Studio is a local, data-driven end-to-end testing workbench. A test analyst uploads an Excel scenario matrix, maps each business step to Playwright actions, optionally reuses actions from a persistent Action Library, supplies test-data iterations, executes scenarios, and reviews screenshots, traces, and run results.

2.2 Business problem

Manual UAT teams need repeatable browser tests without writing a complete test suite by hand. Corporate or air-gapped environments need the application, dependencies, and browsers bundled locally. Test evidence must be saved in a predictable location and must not silently report success when a mapping, data value, or execution failed.

2.3 Users

RoleJob to be doneMust be able to
Test analystTurn a business scenario into a repeatable testUpload Excel, record or manually map, reuse a library action, edit data, execute, inspect evidence.
QA lead / auditorTrust the evidence and failure stateSee exactly which scenario/iteration passed or failed and open its screenshot/result artifacts.
Packager / ITDeliver a no-install target artifactBuild Windows/macOS Electron output; target tester needs no Node, npm, Playwright install, or internet.
Optional LLM operatorAccelerate mapping in an office networkConfigure a compatible internal provider; accept/reject/edit suggestions without making the LLM a required dependency.

2.4 Product promise

  • Excel scenario data becomes a visible, inspectable blueprint.
  • Mappings are stored as executable structured steps, not hallucinated reconstructed arguments.
  • Reusable actions and groups are one canonical library, not a dummy UI cache.
  • Blank data is deliberate; missing data fails loudly.
  • Execution produces evidence and an honest terminal status.
  • Packaged mode keeps writable state outside read-only app.asar.
  • Recording uses an isolated autotest profile by default and does not touch normal Chrome data.

2.5 Non-goals

  • No silent fallback from a failed mapping to an empty passing step.
  • No normal-Chrome profile inspection or deletion.
  • No reset/delete feature for the isolated Chrome profile.
  • No requirement that a target tester install Node/npm or access the internet.
  • No real-device Appium acceptance in the current phase.

4. Scope, users, and governing rules

4.1 In-scope capability map

Blueprint intake

Upload .xlsx, parse scenario/flow/data rows, warn on merged/duplicate rows, persist blueprint and upload.

Mapping

Record with visible Playwright Codegen, manually edit code, parse safe AST steps, preview, replay preceding mapped steps.

Action Library

Persist atomic actions, synonyms, groups/chains; link labels; resolve the same steps in scan, preview, replay, and compiler.

Data Matrix

Harvest {variable} names, save per-scenario iterations, preserve explicit blanks, fail on absent keys.

Execution and evidence

Compile web/mobile output, run with workers/headless choice, capture screenshots/traces/report, render pass/fail dashboard.

Delivery

Web mode for development and Electron NSIS/DMG packaging for target environments; state outside read-only package.

7.3 Execution/results contract

POST /run must compile from the active blueprint, mapping cache, ActionDB resolution, and runtime data; launch the correct runner; put every output under the configured results root; publish terminal status; and produce links that are valid from the app’s current URL in both web and Electron modes.

Target simplification: expose a server-generated result URL/path in the run JSON rather than reconstructing results/${scenarioId}/FINAL.png in browser code. The server knows the actual results root; the browser should not guess it.

8. End-to-end workflows

8.1 Upload to execution

→

→

→

→

→
Evidence
  1. Upload: POST /upload stages and validates the workbook; failure is a visible error.
  2. Scan: parser creates blueprint; scan resolves each label from mappings then ActionDB.
  3. Map: record/manual save writes structured steps; library link writes synonym and mapping cache.
  4. Parameterize: Data Matrix stores iteration overrides; explicit blank is valid, absent key fails.
  5. Compile: compiler resolves mappings/library steps and produces a transient runner file under state root.
  6. Run: server launches Playwright or mobile script and records terminal status.
  7. Evidence: scenario/iteration folder contains screenshots and optional trace/report; UI links use server-known paths.

When the selector is absent, the first diagnostic question is not “is the HTML dummy?” but “did GET /action-db return a valid non-empty canonical library, and did scan classify this row as missing?” The current implementation makes selector rendering conditional on both values.

9.3 Security and trust boundaries

  • Excel, pasted Playwright, LLM output, labels, and data values are untrusted input.
  • Acorn AST extraction and isSafeChain are load-bearing security logic and must not be removed as “complexity.”
  • File uploads are size-limited and unsupported setInputFiles is rejected loudly.
  • Secrets in .env remain local and are never included in this blueprint, tests, commits, or packaged documentation.
  • Normal Chrome profile and its SSO/history/tabs are outside the product’s default access boundary.

12. Acceptance and release gates

12.1 One feature, seven proofs

  1. Gesture: a real user clicks/types/selects in the browser.
  2. Request: browser network log proves method/path/body.
  3. Validation: response status/schema and visible error are asserted.
  4. Write: exact canonical file/database changes are inspected.
  5. Restart: app/server is restarted and state remains.
  6. Consume: scan/preview/compiler/replay/results reads the same state.
  7. Package: test runs against the actual Electron writable path, not only repository mode.

12.2 Release checklist

  • ActionDB path is derived from the canonical writable state resolver.
  • Existing ActionDB is migrated or safely preserved; corrupt files get backup.
  • New Action opens, accepts keyboard input, saves, reloads, and is consumed.
  • Edit opens with stable ID, updates the same record, and does not create a duplicate.
  • Delete removes action/group and group references, then survives restart.
  • New Group opens, lists current actions, persists checked order/IDs, and resolves in compile.
  • Link dropdown appears for every truly missing step when library data exists.
  • Link request updates ActionDB and mappings policy consistently; scan status changes.
  • Execute writes evidence beneath configured results root, not guessed current working directory.
  • PNG, trace, report, and results index links return valid content in web and Electron modes.
  • Run failure is visible, terminal, and not mislabeled completed.
  • Full npm test passes, plus real browser UI and packaged smoke tests.
  • Black-box tester repeats the same scope after every developer fix.

14.4 Open decisions for the next business review

  1. Should deleting an action that is referenced by a saved Excel mapping remove only the library entry, or also invalidate the mapping with a visible warning?
  2. Should “Link to Library” create a synonym only, or replace/create a durable mappings.json entry as the primary link?
  3. Should results be opened inside the Electron window, in the system file manager, or in the default browser?
  4. Should mobile/Appium remain a supported product path now, or be explicitly deferred?
  5. What exact user-facing wording and recovery action is required for an unavailable state root?
  6. Which historical generated files and dead scripts may be deleted after usage verification?
Document boundary: This blueprint documents the current repository and user-reported failures. It does not claim that blockers are fixed and does not change application code.
